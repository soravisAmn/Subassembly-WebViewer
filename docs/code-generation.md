# Code generation: Save (.cs), object → code line, rock-pitching from the web

Thai labels in quotes are the text shown in the web.

## Save (.cs) and the generated code

- On every draw / edit the web generates C#, then **compiles + runs it against the simulator in memory** (Roslyn preview), but **writes to the file only when you press Save (.cs)**.
  - The drawing comes from the in-browser calculator (fast); the web then compares it with the result of running the C#. A mismatch = a red box in Messages.
  - The subassembly's Properties show the status "ผลรันโค้ด C# ตรงกับรูป" · in the tree, ● = the drawn part is not saved yet.
- **Save (.cs)** (blue bar during Edit, Properties, right-click, or Ctrl+S during Edit):
  - An item created with ADD in the web → creates a new file in the folder (the name given at ADD). If a file of that name exists that was not generated by the web, it asks whether to overwrite or rename.
  - A file already generated by the web → replaces only the block marked `SA-DRAWING`; the rest of the file (which you may edit) does not change by a single byte · repeated Saves give the same result.
  - If the marked block was hand-edited (does not match `sa-spec`), the web warns on opening and asks before overwriting on Save.
- Generated files look like hand-written ones (`GetLogicalNames / GetInputParameters / GetOutputParameters / Draw`). The drawn part is in the class `SaDrawing_<class name>` between markers:

  ```
  // ===== SA-DRAWING BEGIN (สร้างโดย SA Drawing Studio — แก้ด้วยการวาดในเว็บ อย่าแก้ช่วงนี้ด้วยมือ) =====
  // sa-spec: {...everything drawn, as one line of JSON...}
  internal static class SaDrawing_LeveeCrest { ... }
  // ===== SA-DRAWING END =====
  ```

  plus 3 calling lines marked `// SA-DRAWING TARGET` / `PARAM` / `CALL` in the main class's methods. Thai comments say which line comes from which point (`// P4 ลาดจนชนดิน`) · parameter limits are checked, using the limit + a warning · Layout mode / no surface draws without ground and does not throw.
- The generated code uses only Civil 3D APIs your files already use, with names checked against API Reference 2027. It should still be built / tried in real Civil 3D.
- **Importing a web-generated file** → the web reads the drawn part back from `sa-spec`; enter Edit and keep drawing.
- An item with no file yet: "✎ แก้โค้ด" / "ดูโค้ดที่สร้าง" opens the code panel read-only, changing with the drawing.
- Parameter names must not clash with names the code uses (e.g. `F`, `cs`, `P1`, C# keywords); the web warns when naming.

## object → code line

Select a point / link / shape (drawn in the web or from hand-written code) → Properties has a **"โค้ด"** group:

- Drawn part: `pavement-assembly.cs บรรทัด 111, 138`: for a point, the coordinate line (`Pt? P3 = …`) + the line adding it to CorridorState (`AddPoint(cs, P3)`); for a link / shape, the `AddLink` / `AddShape` line.
- Hand-written code: the whole call chain, e.g. `บรรทัด 360 (AddShape) ← เรียกจาก 221 (DrawImplement) ← เรียกจาก 130 (Draw)`, every number clickable.
- **"ไปที่โค้ด"** button = opens the code panel at that line and highlights it (purple) · with the panel open, selecting another object follows automatically. (If Monaco cannot load, the fallback panel only scrolls to the line.)
- **The other way**: clicking / moving the cursor in the code panel to a line that creates an object → the object is highlighted on the drawing (purple). A line in a helper function that creates several objects (e.g. `points.Add` in a loop) highlights all objects created by it.
- Line numbers refer to the code that actually ran: the file on disk / the code in the panel (accurate even if unsaved) / code generated from the drawing (items with no file yet). A drawn part in an existing file not yet saved = line numbers of the code after Save → the button becomes **"Save (.cs) แล้วไปที่โค้ด"**.
- How it works: drawn part = the server reads the `SA-DRAWING` block of the code that ran (`CodeGenerator.SourceMap`), so it is correct for new files and for files with the block in the middle · hand-written code = the simulator records who called `Points.Add` / `Links.Add` / `Shapes.Add` using StackTrace + PDB (`SA.Civil3DShim/CallSites.cs`). Line numbers match the real file even though the web inserts RunGuard checkpoints (confirmed by tests with loops / helper functions / local functions).
- Speed: recording lines costs about 37 µs per point (1000 points ≈ 37 ms per run · `base_rock-pitching.cs` runs in 9 ms total), so it is always on. (It can be turned off with `"sites": false` in /api/assembly for files with tens of thousands of points.)

## rock-pitching from the web (round 4e): `base_rock-pitching-web.cs` / `body_rock-pitching-web.cs`

The two files at the root (next to the real files) were drawn with the web's tools and **saved through the same path as the Save (.cs) button** (`/api/drawing/save`). They embed sa-spec, so they can be imported and edited further. The drawing sequence = `buildBase()` / `buildBody()` in `SA.Tests/js/rockpitching.test.js` (the round 4c versions remain at `tests-civil3d/round4c-*.cs`). These root files are now the user's working files; tests compare against locked copies in `SA.Tests/fixtures/`.

- Different from the round 4c versions: parameters have **value types** (`SideSlope` / `FaceSlope` / `EndSlope` = Slope 1:x · width / depth / height / thickness = Length m) · the body's **lower inside point (`SoilBaseInside`) uses Extend to Surface on a vertical line** instead of the expression `min(ground(P1), S0.y)`: an Auxiliary link P1 → S0, then Extend at S0 (ground lower than S0 = extend to the ground · not lower = use S0 → same position as min() in every case) → the real end drops Auxiliary + gets a code, like `SoilToe`.
- Class names `RockPitchingBaseWeb` / `RockPitchingBodyWeb` (same namespace `TestSubassembly` as the real files; names do not clash with `Trapezoid` / `RockPitchingBody`, so they can be built together into Civil 3D).
- `SA.Tests/RockPitchingTests.cs` compares these two against the real files with the same set as round 4c (base 8 / body 7 grounds × Right / Left × 4 value sets); they match in every case (known differences = the "where they differ" table in [civil3d-testing.md](civil3d-testing.md)).
- **View in the web**: "ไฟล์ ▾" → Open project → `rock-pitching-compare.assembly.json` = 2 assemblies on the same ground: "วาดจากเว็บ (-web.cs)" at x = 0 and "ไฟล์จริง (เขียนเอง)" at x = 50 · base on the axis + body attached at base's `TrapTopOutside` · right-click -web → Edit to keep editing. (Or "ไฟล์ ▾" → Import .cs → choose `*-web.cs`, which reads sa-spec back completely.)
- **Build into Civil 3D**: put `base_rock-pitching-web.cs` / `body_rock-pitching-web.cs` in the same .NET project as the real files and build as usual; test per `tests-civil3d/round4c-checklist.md` (by role / code; use the `…Web` classes instead of `Round4c…`).
